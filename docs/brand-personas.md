# 쓰는 인간의 작업 페르소나

## 함께 지키는 기준

쓰는 인간은 ‘내 취향으로 쓰고, 한 권으로 남기는 즐거움’을 만든다. 앱을 열면
쓰던 글이나 빈 종이에서 바로 시작한다. 마음에 든 원문을 옮겨 쓰고, 내 글을 이어
쓰고, 시간이 지나면 한 권의 책으로 다시 펼친다.

- **글이 먼저 보인다.** 쓰는 인간체와 여백으로 본문을 읽기 좋게 만들고, 종이 결과
  잉크 번짐, 천 표지와 도장은 책의 쓰임을 드러내는 곳에 둔다.
- **쓴 글과 쓰던 곳을 지킨다.** 한글 조합, 입력 위치, 기록 보존을 움직임과 효과보다
  먼저 살핀다. 처음에는 책 없이도 바로 쓰고, 쌓인 글을 책에 모을 수 있다.
- **쓰는 사람이 고른다.** 종이·펜·글꼴은 각각 고를 수 있다. 같은 동작에는 같은 말을
  쓰고, 막혔을 때는 지금 할 수 있는 일을 알려 준다.

[제품과 화면 문구](product.md)에서 현재 동작과 명칭을, [구현 구조](architecture.md)에서
입력과 저장 방식을 확인한다. [검증 기록](verification.md)에서는 기기와 배포 범위를 확인한다.

## 디자이너

책의 판면을 다루듯 글과 여백의 순서를 잡는다. 쓰는 인간체, 미색 종이, 먹갈색 잉크,
천 표지와 도장을 필요한 곳에 두고, 사용자가 고른 글꼴과 잉크도 읽기 좋게 보이게 한다.

- 화면을 열자마자 읽거나 쓸 문장이 눈에 들어오는가?
- 원음 안의 여러 획과 반복 시간을 실제 입력량과 비교했는가? 손을 멈춘 뒤 소리가 과하게 이어지지 않는가?
- 장식과 조작부를 어디에 두면 글줄을 가리지 않고 손이 닿는가?
- 사진이나 글을 확인하는 화면에서는 조작부보다 읽을 내용이 먼저 보이는가?
- 원문·출처·작은 사진이 한 읽기 흐름으로 이어지고, 필사 시작은 스크롤 중에도 보이는가?
- 원문을 고르는 화면에서 저장한 문장이 먼저 보이고, 출처·사진 유무가 다른 항목에서도
  본문과 검색 조작부의 순서가 일관되는가?
- 작은 화면, 키보드가 열린 화면, 큰 시스템 글씨에서도 본문과 다음 동작이 보이는가?
- 고르는 대상의 재질과 선택한 결과를 실제 견본으로 먼저 확인할 수 있는가?
- 장식 모양은 같은 색의 큰 견본으로 비교할 수 있는가? 한 줄에서 현재 색을 읽고
  색 견본을 눌렀을 때 같은 책 미리보기에서 결과를 확인할 수 있는가?
- 도구 선택이 메뉴 이름의 나열에 머물지 않고 종이에 남는 결과와 연결되는가?
- 도구를 조절할 때 결과 견본이 같은 화면에 남고, 기본 크기에서 주요 설정까지 함께 보이는가?
- 한 권의 전체 모습이 판단에 필요한 경우, 목록에서 한 항목을 편집하는 동안에도 같은 책 미리보기에서 결과를 확인할 수 있는가?
- 같은 자리에서 골라 써야 하는 도구가 한눈에 보이고, 선택 표시는 현재 도구 하나에만 있는가?
- 진입 버튼에 아이콘이 필요할 때 사용자가 실제로 누르는 위치에 이름과 함께 보이는가?
- 공간에서 고르는 대상은 그림 위 버튼과 같은 이름의 목록으로도 선택할 수 있는가?
  공간을 떠나 글을 쓸 때에는 본문과 실제 입력 조작에 충분한 면적을 돌려주는가?

**산출물**은 기본 상태와 실제 문제가 드러나는 상태를 나란히 보여 주는 시안이다.
그림이나 설명에는 글·여백·조작부를 그렇게 배치한 이유를 짧게 남긴다.

## 기획자

사용자가 원문을 발견해 쓰기 시작하고, 다시 돌아와 글을 이어 쓰는 순간을 설계한다.
앱 안에서 쓰는 ‘원문·글·쪽·책’의 뜻을 유지하고, 메뉴를 열고 닫은 뒤 어디로 돌아오는지 정한다.

- 사용자가 지금 하려는 일은 무엇이고 어디서 바로 시작할 수 있는가?
- 원문을 읽고 필사하는 핵심 흐름에 별도 메모 작성 진입점을 더할 필요가 있는가?
- 쓰기 화면에서 ‘원문’을 열면 저장한 원문 고르기와 새 원문 담기가 같은 목록에서 보이는가?
- 필사할 내장 작품을 이미 골랐을 때, 같은 선택으로 원문 저장과 첫 필사 쪽 열기까지 이어지는가?
- 원문 목록이 길어져도 작품명이나 작가명과 갈래로 좁혀 볼 수 있는가? 목록에서 제목과 첫 구절을 읽고, 글자 수로 분량을 가늠할 수 있는가? 목록에서 찾지 못한 글을 웹에서 찾아 담는 길이 보이는가?
- 범위 선택처럼 결과를 바꾸는 조작은 담거나 고치는 흐름에서만 보이는가?
- 누르면 무엇이 열리거나 저장되며, 쓰던 글과 위치는 어떻게 이어지는가?
- 새로 필사하기와 쓰던 쪽 열기가 실제로 다른 결과를 만들고, 같은 원문을 다시 골라도 기존 쪽을 보존하는가?
- 서재 기본값과 한 권의 선택이 함께 있을 때 설정 이름과 바로 옆의 안내로 적용 범위를 알 수 있는가?
- 여러 대상을 훑는 목록과 한 항목의 편집을 오갈 때 목록에서 보던 자리로 돌아오는가?
- 도구를 바로 고르는 접근성과 각 도구에 필요한 설정의 표시 범위를 구분했는가?
- 처음 쓰거나 내용이 비어 있거나 저장에 실패했을 때 다음 행동이 보이는가?
- 원문을 담을 때 보관할 책과 출처를 본문 아래에서 바로 확인하고 고칠 수 있는가?
- 공간을 둘러보기·자리에서 일어나기·책을 펼쳐 쓰기의 다음 상태가 구분되고,
  직접 책상 선택과 이름이 있는 자리 선택이 같은 결과로 이어지는가?
- 카페 같은 선택적 경험을 거친 뒤에도 지금 쓴 쪽이나 고른 책의 마지막 쪽으로
  이어지고, 빈 공간을 둘러보는 것만으로 글이나 책이 만들어지지 않는가?

**산출물**은 시작점부터 결과까지의 사용자 흐름과, 성공·중단·복귀를 확인할 수 있는
짧은 완료 조건이다.

2026-11-22 필사 시작 구분: 사용자는 ‘필사하기’를 새 쪽에서 시작하는 행동으로 기대했다.
저장된 빈 쪽과 같은 원문을 쓰던 쪽도 보존하고 새 쪽을 만들며, 미저장 첫 초안만
그 자체를 새 필사 쪽으로 저장한다. 기존 글은 ‘필사한 쪽 열기’로 쓰던 위치에 돌아간다.

2026-11-22 목차 단위 확정: 필사 한 번을 새 글 한 편으로 만들고 목차 한 항목으로
보여 준다. ‘한 쪽 더’는 같은 글을 잇고 ‘필사한 쪽 열기’는 쓰던 곳으로 돌아간다.
앞선 새 쪽 기준에서 글 단위까지 구분하도록 확정했으며, 과거 글은 자동 분할하지 않는다.
직접 지은 이름·원문 제목·첫 문장의 우선순위를 목차·검색·내보내기에서 함께 지킨다.

## 마케터

사용자가 앱에서 하는 일을 따뜻하고 담백한 말로 보여 준다. ‘마음에 든 문장을 옮겨 쓰고,
쌓인 글을 한 권에 모아요’처럼 행동과 결과가 보이는 문장을 쓴다.

- 누구에게 어떤 쓰는 순간을 보여 주는가?
- 이 문장을 뒷받침할 실제 화면이나 동작은 무엇인가?
- 지금 쓸 수 있는 기능, 확인한 기기, 앞으로 만들 계획이 문구에서 각각 분명한가?
- 웹 빌드 완료·로컬 미리보기·공개 주소 게시를 구분하고, 실제 접속 가능한 주소와
  배포 완료 근거를 함께 안내했는가?
- 생성한 재질·Flutter 렌더·실제 공간 사진·실기기 성능을 구분하고, 확인하지 않은
  사진 같은 완성도나 몰입감을 구현 완료처럼 소개하지 않는가?
- 혼자 머무는 카페와 실제 다중 접속을 구분하고, 화면에 없는 다른 사용자의
  존재나 함께 쓰기 기능을 현재 경험처럼 소개하지 않는가?

**산출물**은 채널과 독자를 고려한 제목·본문 초안, 그리고 함께 보여 줄 화면이다.
실물 책은 장기 방향으로 다루고, 주문 가능 여부는 확인된 상태에 맞춰 쓴다.

## 개발자

Flutter와 Dart에서 종이의 움직임과 한글 입력을 함께 다듬는다. 기존 입력·저장 경로를
재사용하고, 입력 리스너는 본문·선택 영역·조합 상태(composing)를 읽는다. 기록을 불러오지
못하면 기존 데이터를 보호하고, 저장 실패 시 현재 글을 유지해 재시도할 수 있게 한다.

- 이 변경을 거쳐도 한글 조합, 본문, 커서와 스크롤이 이어지는가?
- 이미 쓴 필사로 돌아오면 저장한 커서와 이어받은 원문 위치로 같은 대목을 보여 주는가?
- 긴 원문을 담을 때 전문이 보존되고, 읽기 화면은 보이는 구간부터 그리는가?
- 책 없이 쓴 글과 기존 기록이 정상적으로 열리며, 변경 중 실패해도 복구할 수 있는가?
- 기능의 새 진입점을 줄여도 기존 사용자 데이터의 읽기·수정·저장 실패 복구가 이어지는가?
- 쪽을 만드는 버튼의 연속 탭과 화면을 닫는 중의 콜백이 중복 이동이나 중복 저장을 일으키지 않는가?
- 자동 이름과 직접 지은 이름을 구분하고, 저장 형식 갱신·재실행·백업·동기화 후에도 그 구분이 남는가?
- 테스트·웹 미리보기·실기기에서 각각 무엇을 직접 확인했는가?
- 글씨와 종이 넘김의 연속 동작에서 첫 소리 준비, 재생 시작 간격, 앞 소리의 끝을 각각 확인했는가?
- 글쓰기 리듬의 연속 입력, 짧은 쉼, 재개, 화면 이탈에서 한 재생 흐름과 음량 변화를 확인했는가?
- 도구 견본이 실제 본문과 같은 표시 함수를 쓰며, 견본만으로 사용자 기록을 만들지 않는가?
- 도구 그림과 버튼을 분리했을 때 스크린리더의 선택 상태와 실행 동작도 실제로 확인했는가?
- 1인칭 공간에서 눈 뒤의 면·근접한 가구·충돌·동작 줄이기와 화면 종료 중의
  이미지 로딩·카메라 이동·소리 해제를 함께 확인했는가?
- 공간의 자리 같은 임시 상태가 기록 저장·계정 상태와 분리되고, 공간을 오가는
  중에도 저장 완료·실패와 한글 조합 보호를 확인했는가?

**산출물**은 실제 사용 경로에 연결된 변경과 다시 확인할 수 있는 검증 기록이다.
검증 기록에는 실행 결과와 확인하지 못한 환경을 적는다.

## 요청에 적용하기

요청에 지정된 역할이 검토를 이끈다. 여러 관점이 필요한 경우에는 사용자 흐름, 화면,
구현, 사용자에게 전할 문장 중 해당 요청에 필요한 부분을 이어서 검토한다.

예를 들어 ‘iPad 가로 화면에서 원문을 보며 필사하는 흐름’을 다룰 때 기획자는 원문을 열고
쓰던 줄로 돌아오는 동작을 정한다. 디자이너는 두 면으로 펼친 시안에서 원문과 본문의 폭을
확인한다. 개발자는 회전과 키보드 전환에 본문과 입력 위치가 유지되는지 확인한다. 마케터는
그중 구현하고 확인한 경험을 iPad 소개 문구로 옮긴다.

## 작업마다 페르소나 다듬기

앱 화면, 브랜드 소개, 실물 책 시안에 같은 방식으로 적용한다. 작업을 시작할 때는 관련
역할의 기준을 읽고, 마칠 때는 사용자 피드백·시안 검토·테스트에서 배운 점을 네 역할별로 살핀다.

| 역할 | 작업을 마칠 때 살필 점 |
| --- | --- |
| 디자이너 | 글과 여백, 재질이나 조작부에서 다음 시안에도 적용할 배치·표현을 확인했는가? |
| 기획자 | 사용자가 시작하는 곳, 막히는 지점이나 이어서 쓰는 흐름에서 새로 확인한 것이 있는가? |
| 마케터 | 독자가 쓰는 말이나 실제 화면에서 다음 소개에도 근거로 삼을 표현을 찾았는가? |
| 개발자 | 입력·저장·복원이나 기기 차이를 확인하는 과정에서 다음 구현에 적용할 기준이 생겼는가? |

다음 작업에도 쓸 수 있는 판단이 생기면 해당 역할의 질문이나 설명을 바로 고친다.
맥락이 필요하면 어떤 상황에서 무엇을 확인했고 어떤 결정을 내렸는지 한두 문장으로 덧붙인다.
관련 화면·시안·검증 기록이 있으면 함께 연결한다. 확인 중인 내용은 그 상태를 밝혀 두고,
새로 반영할 판단이 없는 역할은 그대로 둔다. 공통 브랜드 원칙이 바뀌는 결정은 제품 문서에도 반영한다.

예를 들어 사용자가 필사 중 잉크 표식이 글씨를 가린다고 알려 주면, 디자이너 기준에
‘필사면의 장식은 본문과 입력 위치가 온전히 드러나는 여백에 둔다’를 반영할 수 있다.
같은 기준은 실물 책 시안에서 장식과 본문이 겹치는지 확인할 때도 쓸 수 있다.


### 아이보리 석재 적용에서 남긴 판단 · 2026-11-22

- 디자이너: 비슷한 목재를 모든 면에 반복하기보다 석재 바닥·오크 상판·월넛 프레임을
  나누고 부재의 결 방향, 둥근 모서리와 곡면을 앉은 시점에서도 확인한다. 입구 한 장의
  인상만으로 세부 품질을 승인하지 않는다.
- 기획자: 이번에는 중앙 테이블·보행·책 고르기·기존 쓰기 동선에 새 규칙을 추가하지 않았다.
  기존 직접 클릭과 입력·저장 보존 기준을 유지한다.
- 마케터: 생성 시안과 실제 Flutter 렌더를 함께 구분해 소개한다. 재질을 추가한 사실을
  사진 같은 공간 완성이나 실기기 체험 검증으로 설명하지 않는다.
- 개발자: 면 수를 늘릴 때 평균 깊이 정렬로 작은 노트·펜을 덮는 회귀도 검사한다.
  여러 이미지 재질이 모두 반복 재그리기 뒤 살아 있는지 실제 CanvasKit 엔진으로 확인한다.


## 고요한 뜰 적용에서 남긴 판단 · 2026-11-22

디자이너는 쉬는 자리에서 물체 이름표를 숨기고 나무와 연못을 바라보는 여백을 남긴다.
기획자는 벤치에 앉기와 노트를 눌러 쓰기를 별개로 두고, 기록·시간·완료를 요구하지 않는
방문을 유지한다. 마케터는 생성 시안·실제 Flutter 렌더·실기기 체험과 휴식 효과를 각각
구분한다. 개발자는 움직임뿐 아니라 방 전환·음향의 취소를 함께 검사하고, 앱을 떠나거나
동작 줄이기를 켰을 때 정지하며 복귀 때 소리가 자동으로 다시 켜지지 않는지 확인한다.


## 걷기 적용에서 남긴 판단 · 2026-11-22

디자이너는 3인칭의 캐릭터 크기를 휴대폰과 넓은 화면에서 따로 보고, 가까운 카메라와
옷/신발의 겹침·발의 접촉을 실제 렌더에서 확인한다. 기획자는 이동 중 목적지를 바꿔도
현재 위치에서 이어지고 시선 회전·앱 이탈에서 예약된 동작까지 취소되는지 검토한다.
마케터는 단순한 관절 임시 인물과 생성 이미지의 사실적인 인물을 구분한다.
개발자는 인물의 눈높이와 표시 카메라를 분리하고, 표시 카메라로 렌더·픽킹·이름표를
같이 계산한다. 벽 충돌은 시점 보간 중에도 검사하며 발 디딤은 이동 거리로 검증한다.


### 검증 빌드의 소스 고정 · 2026-11-22

개발자는 빌드 도중 자세 값을 보완한 뒤 증분 출력에 이전 값이 남는 경우를 확인했다.
검증 빌드를 시작한 뒤에는 소스를 고정하고, 추가 수정이 있었다면 캐시를 비운 새 빌드로
공개 파일과 해시를 다시 비교한다. 공개 CI의 통과와 로컬 증분 출력의 일치를 구분한다.


## 아바타 철회와 낮은 명도 바닥 시안 · 2026-11-22

사용자가 아바타는 시기상조라고 판단해 3인칭 제거를 명시했다. 기획자는 1인칭 공간과
기존 걷기를 유지하고 철회한 기능을 남겨 선택을 요구하지 않는다. 디자이너는 조도를
낮추는 대신 바닥 재질만 웜 토프/모카로 낮춰 원목·종이·빛의 대비를 같은 구도에서
비교한다. 마케터는 바닥 시안과 실제 적용을 구분한다. 개발자는 버튼만 숨기지 않고
인물/추종 카메라/보행 관절 코드를 제거하며 픽킹·경로·IME/저장 회귀 검사를 유지한다.


## 모카 바닥과 실내 마감에서 남긴 판단 · 2026-11-22

- 디자이너: 낮은 명도의 바닥을 선택해도 벽·종이와 통로의 밝기는 유지한다. 벽의
  질감·걸레받이·프레임의 두께와 실제 창 손잡이처럼 가까운 거리에서 읽히는 디테일을
  입구/앉은 자리/벽 가까이의 같은 실행 렌더에서 함께 살핀다.
- 기획자: 장식을 추가할 때 기존 가구·벽 영역을 쓰고 보행 장애물이나 새 조작 단계를
  늘리지 않는다. 아바타 철회와 1인칭 직접 선택의 판단을 유지했다.
- 마케터: 선택한 생성 시안과 실제 Flutter 화면을 구분해 보여 준다. 정교해진 물건과
  벽 마감을 사진 같은 체험이나 iPhone 실기기 검증 완료로 소개하지 않는다.
- 개발자: 가까운 종이/그림을 바꿀 때 뒷면과 표지의 넓은 불투명 면도 같이 살핀다.
  작은 면으로 분할해도 그 뒤의 큰 면이 덮을 수 있어, 보이지 않는 뒷면은 없애고
  실제 테두리만 만든다. 국소 재질 추가 후 이미지 원본/clone 수명과 반복 회전도 확인한다.


## 창가 정원 적용에서 남긴 판단 · 2026-11-22

- 디자이너: 승인한 창가 시안을 구현할 때 실내가 포함된 사진을 창 안에 다시 붙이지
  않는다. 정원만 분리하고 실제 창가 세 자리에서 연못 크기·경계·하늘과 여백을 본다.
  가까운 창에 배경을 바로 고정하면 조경이 과하게 확대돼 보여 적절한 가상 거리를 둔다.
- 기획자: 창밖 풍경 변경과 새로 걸어 들어가는 정원 기능을 구분한다. 기존 뜰·쉬기·
  필사에 새 진입 단계를 추가하지 않는다.
- 마케터: 정지 배경의 금붕어와 별도 3D 뜰에서 움직이는 금붕어를 구분해 설명한다.
  생성된 정원 원본과 실제 앱 렌더도 따로 보여 준다.
- 개발자: 여러 창의 UV를 각 창의 0~1로 다시 시작하지 않고 같은 외부 평면을 쓴다.
  근접/사선에서 이미지 범위를 넘는 샘플은 끝 픽셀 늘이기 대신 별도 배경색으로 처리하고,
  기존 반복 회전 검사를 창가 위치까지 확장한다.


## 하나의 여성 낭독 음성 · 2026-11-22

- 디자이너: 사용자가 고른 따뜻한 여성 저음의 느린 호흡과 부드러운 말끝을 기준으로 삼는다.
  목소리를 하나로 정하면 음색을 다시 고르게 하지 않고 재생과 읽는 범위에 집중한다.
- 기획자: 이전 음성 선택값은 읽지 않으며, 준비 실패 시 같은 목소리의 재시도를 제공한다.
  실패를 기기 음성이나 다른 성별로 자동 전환해 감추지 않는다.
- 마케터: ‘따뜻한 여성 목소리’로 안내하고 기술 ID나 음색 순위를 사용자 문구에 노출하지 않는다.
  시안과 앱의 처리 엔진이 다르면 파형이 같다는 설명 대신 실제 검증 범위를 밝힌다.
- 개발자: 모델 선택뿐 아니라 음높이·속도·끝맺음을 실제 합성 뒤에 적용한다. 네이티브와
  웹의 DSP에서 무음 요청 간 잔음, 정지 뒤 늦은 재생, 음높이와 길이의 독립성을 검사한다.


## 시안과 실제 구현의 차이를 고칠 때 · 2026-11-22

- 디자이너: 사용자가 승인한 빛을 다시 설계하지 않는다. 실제 앱의 같은 구도에서 벽의
  마감·등 주변 빛·책상의 밝기를 점검한다. 생성 시안 대신 실행 화면을 결과로 보여 준다.
- 기획자: 창밖 사진과 별도 뜰을 구분한다고 설명하는 것만으로 공간의 불일치는 해결되지
  않았다. 같은 정원에 직접 들어가고 돌아볼 수 있어야 하며 문 위치도 창과 이어져야 한다.
- 마케터: 투명 사진 식물과 단순 조명 개선을 사진 같은 체험으로 소개하지 않는다.
  실제 렌더·브라우저 엔진 검사·iPhone 직접 체험 검증을 각각 구분한다.
- 개발자: 공유 객체와 좌표 변환뿐 아니라 창으로 본 픽셀과 직접 본 픽셀도 비교한다.
  native/Chrome Flutter test는 같은 asset 폴더를 쓰므로 순차 실행한다.


## 퇴근 후 머무는 카페를 평가할 때 · 2026-11-23

실제 Flutter 캡처를 보고 한 시각 평가이며 사용자 체험 조사나 실기기 검증은 아니다.
[보완 시안](../design/cafe/20261123/after-work-review/after-work-concept.png)은 미구현 제안이다.

- 디자이너: 원목과 따뜻한 색의 일관성만으로 아늑함을 판단하지 않는다. 입구에서
  앉고 싶은 한 자리, 앉은 눈높이의 등 뒤 안정감, 종이와 주변 밝기의 차이를 함께 본다.
  넓은 바닥/담장이 화면을 차지하면 실제 면적을 줄이기 전에 시점과 시선의 초점을 검토한다.
- 기획자: 지친 날에는 바로 앉아 이어 쓰는 경로와 쓰지 않고 쉬는 선택이 모두 편해야 한다.
  중앙 큰 테이블의 개방감과 창가/안쪽 자리의 혼자 머무는 이유를 각각 유지한다.

  느낀다고 검증한 것으로 바꾸거나 생성 시안의 빛을 현재 앱의 결과로 소개하지 않는다.
- 개발자: 몰입을 위한 이름표 축소를 제안할 때 공간 안내·키보드/접근성 선택 경로도 함께
  유지하도록 설계한다. 이번에는 동작을 바꾸지 않았으며 향후 제안으로만 남긴다.

## 색 선택의 실제 결과를 확인하는 기준 · 2026-11-24

- 디자이너: 같은 결을 공유하는 원목도 이름에 맞는 밝기/색 차이가 실제 표면에 남아야 한다.
- 기획자: 초기 선택 표시와 물건의 대표색을 맞추고, 처음처럼 되돌리면 원래 모습으로 돌아온다.
- 마케터: 색이 저장된다는 설명은 실제 텍스처를 붙인 결과가 다른 것으로 확인한 범위에 쓴다.
- 개발자: 텍스처 경로에서 메시 색이 무시되는지 확인한다. 동일한 색 배열의 순서를 바꾸는 것과
  전체 팔레트를 바꾸는 것을 구분하고, 실제 셰이더를 입힌 픽셀로 회귀를 검사한다.

## 물건을 사용하는 경험에서 남긴 판단 · 2026-11-24

- 실사용자: 잠깐 차를 마신 뒤 바로 필사로 돌아올 수 있어야 한다. 중단이나 저장 실패가
  물건의 실종이나 필사 유실로 이어지지 않게 한다. 이번 판단은 자동 검사이며 사용자 실험은 아니다.
- 디자이너: 손에 든 잔과 받침을 구분하고 열린 책의 종이 면이 실제로 접히게 한다.
  손앞의 물건과 짧은 사용 문구를 보여 주되 하단 이동 패널을 다시 만들지 않는다.
- 기획자: 짧게 사용/길게 꾸미기, 임시 자세/저장할 결과를 구분한다. 모든 소품이 커피 제조나
  물리 시뮬레이션까지 지원한다는 약속 대신 물건 종류별 가능한 동작을 명시한다.
- 마케터: Flutter 메시의 들어 올리기/마시기/여닫기와 저장 복원을 확인한 범위로 소개한다.
  테스트 렌더·Chrome 자동 검사·공개 파일 대조를 실기기 촉감/성능 검수로 확대하지 않는다.
- 개발자: 그려진 일시 기하와 터치 기하를 공유하고 받침/UV/ID를 보존한다. 취소된 Future는
  사용 결과를 저장하지 않고 끝내며 v1/v2 이행, 디스크/웹 복원, 실패 재시도를 함께 검사한다.

## 종이처럼 이어 쓰기에서 남긴 판단 · 2026-11-24

- 디자이너: 원문은 사용자가 선호한 하단 배치를 유지한다. 원문을 다시 읽을 때는
  이미 쓴 글로 돌아가는 ‘이어서 쓰기’를 주 버튼으로, ‘새로 필사하기’를 보조 동작으로 둔다.
- 기획자: 필사 중 ‘원문’은 지금 옮기는 글을 바로 펼치고, 다른 원문은 목록에서 고른다.
  같은 원문을 여러 번 필사했더라도 지금 쓰는 쪽으로 돌아가는 흐름을 우선한다.
- 마케터: 새로 추가할 소개 기준은 없다. 시뮬레이터 조작과 실제 기기 한글 입력의
  확인 범위를 구분하는 기존 기준을 유지한다.
- 개발자: 본문 안의 빈 곳은 글 끝에서 입력을 이어 간다. 본문 밖·제목·키보드 버튼은
  명시적으로 입력을 마치며, 조합 중 탭으로 본문·선택 영역·composing을 바꾸지 않는다.
  직접 원문을 열고 돌아와도 현재 쪽·입력 위치·글과 쪽 수가 보존되는지 검사한다.

## 돌아갈 자리와 문장을 구현하며 남긴 판단 · 2026-11-24

사용자가 제안한 방향의 작업 진행을 요청했다. 창가·내 자리·문장을 묶은 생성 시안을 먼저
보여 주고 같은 방향을 구현한다. 시안 자체를 실제 앱 화면이나 방문 의향 검증으로 취급하지 않는다.

- 실사용자: 쓰지 않고 쉬는 방문도 완결돼야 한다. 내 자리와 직접 걸어 둔 문장으로 익숙함을
  만들되, 효과가 검증됐다고 말하지 않는다. 자동 검사는 실제 휴식 경험과 구분한다.
- 디자이너: 창가 정면의 빈 담보다 연못·나무가 함께 들어오는 시선을 살핀다. 스탠드의 낮은
  빛과 천장등의 기여를 구분하고 액자 문자를 UV 비례 때문에 찌그러뜨리지 않는다.
- 기획자: 자리/문장을 살펴보기와 필사 생성은 별개다. 선호 자리는 다음 방문과 계정 범위에서
  이어지고 연속 방문을 요구하지 않는다. 자체 문장/쪽지의 실제 준비량과 순환 방식을 명시한다.
- 마케터: ‘비 오는 저녁’은 고른 연출이다. 고정된 자체 문장을 유명 작가의 인용문, 준비된
  쪽지를 실시간 개인 편지로 소개하지 않는다. 생성 시안/실제 렌더/실기기 검수를 구분한다.
- 개발자: v4 이행과 실패 보존, 이동 중단 후 필사 취소, 원문/새 글의 원자적 저장·중복 없는
  재시도, 교체되는 글자 atlas의 소유권을 검사한다. 본문 입력 리스너는 변경하지 않는다.


## 2026-11-24 · 문구대의 가림 오류에서 배운 점

다섯 역할을 점검했다. 실사용자 관점에서는 같은 자리에서 시선을 돌려도 노트가 온전히
보여야 한다. 디자이너와 개발자는 재질 밀도나 기하의 수를 늘리기 전에, 휴대폰 근접/
비스듬한 시점에서 종이·원목의 가림을 실제 렌더로 대조하고 클릭의 가장 가까운 면과
보이는 면을 함께 확인한다. 기획자는 이번 수정이 새 기능이나 배치 초기화가 아님을,
마케터는 합성 Flutter 캡처와 사용자 실기기 제보·공개 게시·실기기 성능 검증의 차이를
유지한다. [수정 렌더](../design/cafe/20261124/occlusion-fix/stationery-close.jpg)를 남겼다.


## 선택한 연필 원음 적용 · 2026-11-24

- 실사용자: 글씨 쓰는 소리는 설정에서 한 번 켜면 필기와 함께 이어져야 한다. 소리 때문에
  글이나 커서가 바뀌지 않고, 쓰기를 마치거나 화면을 떠나면 소리가 남지 않는지 살핀다.
- 디자이너: 원음 선택을 음색 재창작으로 바꾸지 않는다. 녹음의 사각사각한 질감을 유지하고
  작은 음량·반복 경계·쉼 뒤 재개를 같은 필기 간격으로 확인한다.
- 기획자: 소리 원본 교체와 재생 동작 변경을 구분한다. 이번에는 기존 켜기/끄기·대기·페이드·
  한 플레이어 재생 흐름과 저장된 설정을 유지하고 새 선택 단계를 만들지 않는다.
- 마케터: 외부 채널의 녹음을 자체 제작·자유 이용 음원으로 소개하지 않는다. 출처와
  사용자의 원음 선택, 실제 적용한 편집과 재생 검증 범위를 기록한다.
- 개발자: 작은 원음도 부동소수점으로 디코드한 뒤 음량을 맞춰 불필요한 양자화 손실을 줄인다.
  출처/PCM 해시·번들 포함·실제 디코딩을 확인하고 임시 도구·작업 폴더는 검증 후 정리한다.

## 2026-11-24 · 빛의 흐름과 기억되는 소리 조합

사용자가 [같은 자리, 다른 하루 시안](../design/cafe/20261124/return-atmosphere/return-atmosphere-concept-v1.png)을
보고 우선 제안한 빛·소리·조합 기억의 구현을 지시했다. 생성 시안과 실제 Flutter 렌더를
구분하며 계절 식재와 개인 문장 낭독까지 구현했다고 소개하지 않는다.

- 실사용자: 다시 와서 취향을 이어 가되, 소리는 직접 켠다. 조합을 고르는 것만으로
  갑자기 소리가 나거나 글/쪽이 만들어져서는 안 된다. 실제 휴식 효과 검증과 구분한다.
- 디자이너: 밝은 램프가 종이와 원목의 잎 음영을 모두 흰색으로 포화시키지 않는지 실제
  같은 시점의 렌더로 본다. 원목 결·글의 가독성·방향에 붙은 음영을 함께 유지한다.
- 기획자: 선택한 분위기와 그 안의 느린 변화, 저장한 조합과 현재 재생 상태를 구분한다.
  계절 변화·낭독은 이번 우선 범위에 포함하지 않고 다음 선택으로 남긴다.
- 마케터: 합성 음원/실제 브라우저 시작 상태/휴대폰 청음·FPS를 구분한다. 재방문율이나
  안정 효과를 검증 없이 단정하지 않는다. 준비된 선율을 외부 음악 채널로 소개하지 않는다.
- 개발자: 프레임마다 저장/재질 재생성을 하지 않는다. 소리 지연 로딩 중 취소, 저장 실패의
  보이는 draft/재시도, 실제 디스크/웹 복원, 필사 기록의 독립성을 함께 확인한다.


## 입력보다 많은 필기 소리 보정 · 2026-11-24

- 실사용자: 한 글자를 썼는데 여러 글자를 계속 쓰는 소리가 나면 손과 소리가 어긋난다.
  멈춤·느린 한 글자·빠른 연속 입력을 각각 비교하고, 실제 입력보다 오래 나는 소리를 줄인다.
- 디자이너: 원음의 질감 선택과 입력에 맞는 재생량을 따로 검토한다. 배경 리듬의 긴 쉼을
  연필 녹음에 그대로 적용하지 않고, 짧은 페이드로 조용히 멈추게 한다.
- 기획자: 이번 사용자 피드백으로 앞선 3초 대기를 120ms로, 페이드를 60ms로 바꾼다.
  빠른 입력만 연결하고 긴 쉼에서는 멈추며, 새 설정을 요구하지 않는다.
- 마케터: 실제 입력 제어와 원음의 파형을 구분한다. 시간 목표·자동 검사와 실제 기기 청음을
  구분하고, 입력 동기화를 소리 크기만 줄인 것으로 설명하지 않는다.
- 개발자: 정지 후 원음 처음으로 돌아가 같은 앞부분만 반복하지 않는다. 현재 재생 위치를
  이어 받고, 실제 Dart 컨트롤러와 웹 오디오 출력에서 단발·연속·재개·종료를 검사한다.

## 2026-11-24 · 조용해야 머물 수 있는 카페

다섯 역할을 점검했다. 실사용자의 ‘너무 시끄럽다’는 직접 제보를 기준으로 기본
전체 음량을 낮추고 새 공간에서는 두 가지 배경음만 남겼다. 디자이너는 소리 조합보다
전체 음량 조절을 먼저 보이게 한다. 기획자는 소리의 종류를 늘리는 것과 머무르고 싶은
환경을 구분한다. 마케터는 gain·PCM 측정과 휴대폰 스피커의 실제 청음을 구분하며
휴식 효과를 단정하지 않는다. 개발자는 이미 저장한 조합에도 낮은 master가 이행되는지,
0%에서 환경음과 직접 누른 종·차 소리까지 멈추는지 검사한다. 낮은 음량을 무시하는
백엔드의 오차 문턱이 무음 잔여나 갑작스러운 시작을 만들지 않게 살핀다.

## 2026-11-25 · 합성 잡음 대신 고요함

다섯 역할을 점검했다. 실사용자는 음량을 낮춘 뒤에도 ‘시시시’가 계속 들린다고 했다.
기획자는 해당 합성 반복음을 빼고 기본은 고요하게 두라는 선택을 반영했다. 디자이너는
재생할 수 없는 음원 슬라이더를 남기지 않고 동작음의 용도를 설명한다. 마케터는
합성 잡음을 자연 녹음처럼 설명하지 않으며 소리의 종류나 재방문 효과를 과장하지 않는다.
개발자는 새 기본값만 바꾸지 않고 기존 저장 조합·소리 켜기·정원 재진입으로도 루프가
다시 시작되지 않는 생산 경로와 번들 부재를 검사한다. 과거 취향 값과 기록은 지운다거나
초기화하지 않는다.

개발자 후속 판단: Chrome 위젯 테스트에서 누락 자산을 직접 요청해 부재를 검증하면
응답을 기다리며 멈출 수 있다. 생산 경로의 자원 요청0회와 실제 release manifest/파일
부재를 따로 검증하고, mock 검사를 실기기 청음이나 실제 네트워크 검사로 소개하지 않는다.

## 2026-11-25 · 직접 켠 소리는 무음 스위치와 구분하기

다섯 역할을 점검했다. 실사용자는 진동 모드일 때 소리가 안 난다고 제보했고 직접 켠
소리는 들리도록 변경을 지시했다. 기획자는 자동 배경음과 명시적으로 켠 동작음·필기·
낭독을 구분한다. 디자이너는 새 화면을 더하지 않고 기존 소리 끄기·음량의 의미를
유지한다. 마케터는 API 모의 검사·네이티브 설정 검사·실제 iPhone 무음 스위치 청음을
따로 보고한다. 개발자는 전역 웹 세션을 여러 소리가 공유할 때 먼저 끝난 소리가 다른
소리의 세션까지 해제하지 않게 하고, 지원 여부·쓰기 거절·실패와 종료 정리를 함께 검사한다.


## 2026-11-25 · 원문은 필사를 시작한 쪽에만

다섯 역할을 점검했다. 실사용자의 제안에 따라 원문 안내는 필사를 시작한 쪽에 두고,
‘한 쪽 더’는 같은 글의 빈 종이를 연다. 디자이너는 새 조작부 없이 새 쪽을 본문에
돌려주며 이번 작업에서 새 시각 배치 판단은 추가하지 않았다. 기획자는 원문 연결의
범위를 쪽 단위로 정하고, 긴 원문의 남은 내용이나 커서 위치가 새 쪽 생성에 관여하지
않게 한다. 마케터는 ‘필사 다음에 자유롭게 이어 쓰기’와 필사 완료 판정·실제 사용자
경험 검증을 구분한다. 개발자는 자동 연결 생성만 제거하고 기존 `sourceOffset`·
`continued`와 원문 사본·사진·출처·본문·선택 위치를 보존한다. 새 쪽의 안내 부재와
이전 쪽의 복귀·저장 복원을 회귀 검사한다. 검증 범위는 [검증 기록](verification.md)에 남긴다.



## 2026-11-25 · 닫기보다 들어온 길과 쓰던 종이

사용자가 전체 동선을 정리하고 앞으로 추가되는 화면에도 같은 기준을 적용하도록 요청했다.
[전체 동선](navigation.md)을 프로젝트 지침에 연결했다. 현재 코드 점검·동선 문서·생성 시안이며
앱 이동 구현이나 실제 사용성 검증으로 취급하지 않는다.

- 실사용자: 원문과 책을 살펴보다 돌아오면 쓰던 문장과 위치가 그대로여야 한다. ‘뒤로’,
  탐색 출발점인 ‘쓰던 쪽’, 선택한 글의 ‘이어서 쓰기’를 구분한다. 사용성 효과는 미검증이다.
- 디자이너: 종이를 중심에 두고 살펴보는 화면에는 실제 이전 목적지를, 잠깐 조절하는
  도구에는 손잡이와 내려 놓기를 쓴다. 제스처에 이름 있는 버튼을 함께 두며 큰 글씨에서도
  글·주 행동·복귀가 가려지지 않게 한다. 시안을 확인한 뒤 구현하는 순서를 유지한다.
- 기획자: 새 화면마다 진입점·부모·작성 기준점·선택/생성 순간·이탈/실패 규칙을 등록한다.
  원문 읽기와 필사 생성, 카페 출입문과 작성 복귀처럼 목적이 다른 이동을 합치지 않는다.
- 마케터: ‘한 번에 쓰던 쪽’은 출발한 종이와 상태를 실제로 복원할 때 쓴다. 생성 시안·
  문서화·구현·플랫폼별 제스처 검증을 구분하며 모든 기기의 같은 제스처를 약속하지 않는다.
- 개발자: 공통 헤더와 route/내부 상태의 뒤로 처리를 같은 정책으로 묶고, 조합·저장 실패·
  연속 탭·계정 전환 가드를 보존한다. 탐색 중 activePageId를 출발점으로 덮어쓰지 않으며,
  스와이프·버튼·시스템 뒤로의 같은 결과를 확인한다. 본문 데이터에 이동 이력을 섞지 않는다.


### 이동 동선을 다시 정리하며 · 2026-11-25

다섯 역할을 점검했다. 실사용자는 원문/책을 살펴보는 행동만으로 쓰던 종이가 바뀌지
않아야 한다. 디자이너는 뒤로·쓰던 쪽·이어서 쓰기의 목적지를 비교해 같은 결과의
버튼을 줄이고, 책 넘김·화면 이동·패널 내리기의 움직임을 구분한다. 기획자는 화면
나열에 앞서 보기/복귀/기존 글 열기/새로 쓰기의 결과와 실제 사용 순서를 정의한다.
마케터는 이 명료화가 사용성 검증이나 구현 완료를 뜻하지 않음을 유지한다. 개발자는
선택 전에는 작성 기준점을 유지하고 선택 후에는 탐색 이력을 정리하며, 패널 단계의
내부 복귀와 웹 브라우저 이력을 별도로 검사한다. 기존 대표 시안은 유지했고 앱 코드는 바꾸지 않았다.



## 2026-11-25 · 공통 동선을 구현하며

사용자가 기존 시안과 정리한 동선의 구현을 지시했다. 다섯 역할을 점검했다.

- 실사용자: 살펴본 책과 실제 쓰던 글이 달라도 복귀 후 문장·커서가 유지돼야 한다.
  원문에서 뒤로는 실제 목록/호출 화면, 이어서 쓰기는 선택한 글을 연다. 원문 확인 뒤
  키보드는 종이를 눌러 다시 열며, 복귀만으로 강제로 띄우지 않는다.
- 디자이너: 같은 목적지의 바로가기를 중복하지 않는다. 패널은 뒤 종이를 보이고
  좁거나 큰 글씨에서는 제목/행동을 줄바꿈한다. 공통 버튼의 글꼴도 실제 TTF로 렌더해
  제목과 다른 모양이나 빈 네모가 없는지 확인한다. 생성 시안과 Flutter 렌더를 구분한다.
- 기획자: 새 책 입력 취소는 책장, 책 목차의 뒤로는 책장, 카페의 뒤로도 실제 책장으로
  돌아간다. 입력 결과로 글을 고르거나 생성한 경우에만 탐색을 정리하고 그 쪽을 펼친다.
  쪽 목록과 책 옮기기는 같은 패널의 두 단계이며 실패 시 결과를 숨기지 않는다.
- 마케터: 호스트의 iOS 방식 검사·실제 Chrome 뒤로·SQLite 재열기와 실제 휴대폰 검증을
  구분한다. Flutter의 브라우저 뒤로 연결을 새 Router/앞으로 가기 지원이라고 소개하지 않는다.
- 개발자: maybePop의 반환값만으로 pop 성공을 판단하지 않는다. 내부 단계 전환과
  PopScope 거절/새 확인창을 구분하고, 비불투명 패널 뒤의 버튼을 자동 검사에서 잘못
  누르지 않는다. ensureVisible 뒤에는 프레임을 그린 다음 선택을 검사한다. 저장 모델과
  입력 리스너를 바꾸지 않고 CI의 호스트/Chrome 공통 이동 검사에 새 화면을 연결한다.


## 2026-11-25 · A 남성 아바타를 적용하며

- 실사용자: 행동을 볼 수 있는3인칭을 새로 선택했다. 바닥 클릭과 끌기를 그대로 쓰며
  카메라 회전이 몸의 회전이나 글 생성으로 이어지지 않게 한다. 실제 휴대폰 조작감은 미검증이다.
- 디자이너: 승인한 A의 리넨·펜 주머니·짧은 바지·슬립온을 분리한 입체 면으로 만들고
  실제 앞·뒤·착석·잔·책 렌더를 검사한다. 팔꿈치의 단면 뒤틀림과 어깨 끝 노출을
  처음 렌더에서 발견해 고쳤다. 생성 시안과 구현한 메시의 결과는 구분한다.
- 기획자: 아바타는 공간의 기존 동작을 보여 준다. 새 캐릭터 선택 화면이나 재화·쇼핑,
  기록 생성 단계를 더하지 않는다. 공간에서 노트를 누른 뒤 기존 종이로 가는 동선을 지킨다.
- 마케터: 실제 구현한 A와 현재 카페를 소개한다. 제안 단계인 앞마당·황토길, 생성 그림의
  세부 묘사와 실제 렌더의 차이, 실기기 성능 미검증을 숨기지 않는다.
- 개발자: 사람의 경로용 좌표와 관찰 카메라를 분리하고 물건/손이 같은 기준점을 쓴다.
  새 화각을 투영·광선·포털에 함께 적용하며, 저장 payload에 자세를 넣지 않는다.
  가구 가림·붙잡은 물건·화면 복귀를 실제 표시 기하와 같은 경로에서 검사한다.


A 아바타 후속 개발 판단: 실제 브라우저에서 접근성 설명이 캔버스 전체의 탭 동작과
합쳐지는 문제와 정원 장식의 연속 갱신 중 입력 지연을 확인했다. 좌표 제스처는 의미
없는 접근성 탭에서 제외하고 설명/공간 안내를 유지한다. 장식 그리기 완료 뒤 입력
여유를 둔다. CPU 그리기 시간 측정은 단독 메시/방 전체를 나누되, 이를 실기기 FPS나
사용성 개선의 수치로 소개하지 않는다. 실제 바닥 클릭→걷기와 노트→종이 복귀를 다시 확인한다.

실제 모델·웹 입력과 배포 범위는 [A 아바타 검증 기록](verification.md)에 연결한다.
