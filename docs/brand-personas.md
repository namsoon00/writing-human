# 쓰는 인간의 작업 페르소나

## 함께 지키는 기준

쓰는 인간은 ‘내 취향으로 쓰고, 한 권으로 남기는 즐거움’을 만든다. 앱을 열면
쓰던 글이나 빈 종이에서 바로 시작한다. 마음에 든 원문을 옮겨 쓰고, 내 글을 이어
쓰고, 시간이 지나면 한 권의 책으로 다시 펼친다.

- **글이 먼저 보인다.** 쓰는 인간체와 여백으로 본문을 읽기 좋게 만들고, 종이 결과
  잉크 번짐, 천 표지와 도장은 책의 쓰임을 드러내는 곳에 둔다.
- **쓴 글과 쓰던 곳을 지킨다.** 한글 조합, 입력 위치, 기록 보존을 움직임과 효과보다
  먼저 살핀다. 처음에는 책 없이도 바로 쓰고, 쌓인 글을 책에 모을 수 있다.
- **쓰는 사람이 고른다.** 종이·펜·글꼴은 각각 고를 수 있다. 같은 동작에는 같은 말을
  쓰고, 막혔을 때는 지금 할 수 있는 일을 알려 준다.

[제품과 화면 문구](product.md)에서 현재 동작과 명칭을, [구현 구조](architecture.md)에서
입력과 저장 방식을 확인한다. [검증 기록](verification.md)에서는 기기와 배포 범위를 확인한다.

## 디자이너

책의 판면을 다루듯 글과 여백의 순서를 잡는다. 쓰는 인간체, 미색 종이, 먹갈색 잉크,
천 표지와 도장을 필요한 곳에 두고, 사용자가 고른 글꼴과 잉크도 읽기 좋게 보이게 한다.

- 화면을 열자마자 읽거나 쓸 문장이 눈에 들어오는가?
- 글쓰기 리듬은 낮은 두 음의 여운이 잠깐 쉬는 동안에도 이어지고, 글을 마칠 때 서서히 잦아드는가?
- 장식과 조작부를 어디에 두면 글줄을 가리지 않고 손이 닿는가?
- 사진이나 글을 확인하는 화면에서는 조작부보다 읽을 내용이 먼저 보이는가?
- 원문·출처·작은 사진이 한 읽기 흐름으로 이어지고, 필사 시작은 스크롤 중에도 보이는가?
- 원문을 고르는 화면에서 저장한 문장이 먼저 보이고, 출처·사진 유무가 다른 항목에서도
  본문과 검색 조작부의 순서가 일관되는가?
- 작은 화면, 키보드가 열린 화면, 큰 시스템 글씨에서도 본문과 다음 동작이 보이는가?
- 고르는 대상의 재질과 선택한 결과를 실제 견본으로 먼저 확인할 수 있는가?
- 장식 모양은 같은 색의 큰 견본으로 비교할 수 있는가? 한 줄에서 현재 색을 읽고
  색 견본을 눌렀을 때 같은 책 미리보기에서 결과를 확인할 수 있는가?
- 도구 선택이 메뉴 이름의 나열에 머물지 않고 종이에 남는 결과와 연결되는가?
- 도구를 조절할 때 결과 견본이 같은 화면에 남고, 기본 크기에서 주요 설정까지 함께 보이는가?
- 한 권의 전체 모습이 판단에 필요한 경우, 목록에서 한 항목을 편집하는 동안에도 같은 책 미리보기에서 결과를 확인할 수 있는가?
- 같은 자리에서 골라 써야 하는 도구가 한눈에 보이고, 선택 표시는 현재 도구 하나에만 있는가?
- 진입 버튼에 아이콘이 필요할 때 사용자가 실제로 누르는 위치에 이름과 함께 보이는가?
- 공간에서 고르는 대상은 그림 위 버튼과 같은 이름의 목록으로도 선택할 수 있는가?
  공간을 떠나 글을 쓸 때에는 본문과 실제 입력 조작에 충분한 면적을 돌려주는가?

**산출물**은 기본 상태와 실제 문제가 드러나는 상태를 나란히 보여 주는 시안이다.
그림이나 설명에는 글·여백·조작부를 그렇게 배치한 이유를 짧게 남긴다.

## 기획자

사용자가 원문을 발견해 쓰기 시작하고, 다시 돌아와 글을 이어 쓰는 순간을 설계한다.
앱 안에서 쓰는 ‘원문·글·쪽·책’의 뜻을 유지하고, 메뉴를 열고 닫은 뒤 어디로 돌아오는지 정한다.

- 사용자가 지금 하려는 일은 무엇이고 어디서 바로 시작할 수 있는가?
- 원문을 읽고 필사하는 핵심 흐름에 별도 메모 작성 진입점을 더할 필요가 있는가?
- 쓰기 화면에서 ‘원문’을 열면 저장한 원문 고르기와 새 원문 담기가 같은 목록에서 보이는가?
- 필사할 내장 작품을 이미 골랐을 때, 같은 선택으로 원문 저장과 첫 필사 쪽 열기까지 이어지는가?
- 원문 목록이 길어져도 작품명이나 작가명과 갈래로 좁혀 볼 수 있는가? 목록에서 제목과 첫 구절을 읽고, 글자 수로 분량을 가늠할 수 있는가? 목록에서 찾지 못한 글을 웹에서 찾아 담는 길이 보이는가?
- 범위 선택처럼 결과를 바꾸는 조작은 담거나 고치는 흐름에서만 보이는가?
- 누르면 무엇이 열리거나 저장되며, 쓰던 글과 위치는 어떻게 이어지는가?
- 새로 필사하기와 쓰던 쪽 열기가 실제로 다른 결과를 만들고, 같은 원문을 다시 골라도 기존 쪽을 보존하는가?
- 서재 기본값과 한 권의 선택이 함께 있을 때 설정 이름과 바로 옆의 안내로 적용 범위를 알 수 있는가?
- 여러 대상을 훑는 목록과 한 항목의 편집을 오갈 때 목록에서 보던 자리로 돌아오는가?
- 도구를 바로 고르는 접근성과 각 도구에 필요한 설정의 표시 범위를 구분했는가?
- 처음 쓰거나 내용이 비어 있거나 저장에 실패했을 때 다음 행동이 보이는가?
- 원문을 담을 때 보관할 책과 출처를 본문 아래에서 바로 확인하고 고칠 수 있는가?
- 공간을 둘러보기·자리에서 일어나기·책을 펼쳐 쓰기의 다음 상태가 구분되고,
  직접 책상 선택과 이름이 있는 자리 선택이 같은 결과로 이어지는가?
- 카페 같은 선택적 경험을 거친 뒤에도 지금 쓴 쪽이나 고른 책의 마지막 쪽으로
  이어지고, 빈 공간을 둘러보는 것만으로 글이나 책이 만들어지지 않는가?

**산출물**은 시작점부터 결과까지의 사용자 흐름과, 성공·중단·복귀를 확인할 수 있는
짧은 완료 조건이다.

2026-11-22 필사 시작 구분: 사용자는 ‘필사하기’를 새 쪽에서 시작하는 행동으로 기대했다.
저장된 빈 쪽과 같은 원문을 쓰던 쪽도 보존하고 새 쪽을 만들며, 미저장 첫 초안만
그 자체를 새 필사 쪽으로 저장한다. 기존 글은 ‘필사한 쪽 열기’로 쓰던 위치에 돌아간다.

2026-11-22 목차 단위 확정: 필사 한 번을 새 글 한 편으로 만들고 목차 한 항목으로
보여 준다. ‘한 쪽 더’는 같은 글을 잇고 ‘필사한 쪽 열기’는 쓰던 곳으로 돌아간다.
앞선 새 쪽 기준에서 글 단위까지 구분하도록 확정했으며, 과거 글은 자동 분할하지 않는다.
직접 지은 이름·원문 제목·첫 문장의 우선순위를 목차·검색·내보내기에서 함께 지킨다.

## 마케터

사용자가 앱에서 하는 일을 따뜻하고 담백한 말로 보여 준다. ‘마음에 든 문장을 옮겨 쓰고,
쌓인 글을 한 권에 모아요’처럼 행동과 결과가 보이는 문장을 쓴다.

- 누구에게 어떤 쓰는 순간을 보여 주는가?
- 이 문장을 뒷받침할 실제 화면이나 동작은 무엇인가?
- 지금 쓸 수 있는 기능, 확인한 기기, 앞으로 만들 계획이 문구에서 각각 분명한가?
- 웹 빌드 완료·로컬 미리보기·공개 주소 게시를 구분하고, 실제 접속 가능한 주소와
  배포 완료 근거를 함께 안내했는가?
- 생성한 재질·Flutter 렌더·실제 공간 사진·실기기 성능을 구분하고, 확인하지 않은
  사진 같은 완성도나 몰입감을 구현 완료처럼 소개하지 않는가?
- 혼자 머무는 카페와 실제 다중 접속을 구분하고, 화면에 없는 다른 사용자의
  존재나 함께 쓰기 기능을 현재 경험처럼 소개하지 않는가?

**산출물**은 채널과 독자를 고려한 제목·본문 초안, 그리고 함께 보여 줄 화면이다.
실물 책은 장기 방향으로 다루고, 주문 가능 여부는 확인된 상태에 맞춰 쓴다.

## 개발자

Flutter와 Dart에서 종이의 움직임과 한글 입력을 함께 다듬는다. 기존 입력·저장 경로를
재사용하고, 입력 리스너는 본문·선택 영역·조합 상태(composing)를 읽는다. 기록을 불러오지
못하면 기존 데이터를 보호하고, 저장 실패 시 현재 글을 유지해 재시도할 수 있게 한다.

- 이 변경을 거쳐도 한글 조합, 본문, 커서와 스크롤이 이어지는가?
- 이미 쓴 필사로 돌아오면 저장한 커서와 이어받은 원문 위치로 같은 대목을 보여 주는가?
- 긴 원문을 담을 때 전문이 보존되고, 읽기 화면은 보이는 구간부터 그리는가?
- 책 없이 쓴 글과 기존 기록이 정상적으로 열리며, 변경 중 실패해도 복구할 수 있는가?
- 기능의 새 진입점을 줄여도 기존 사용자 데이터의 읽기·수정·저장 실패 복구가 이어지는가?
- 쪽을 만드는 버튼의 연속 탭과 화면을 닫는 중의 콜백이 중복 이동이나 중복 저장을 일으키지 않는가?
- 자동 이름과 직접 지은 이름을 구분하고, 저장 형식 갱신·재실행·백업·동기화 후에도 그 구분이 남는가?
- 테스트·웹 미리보기·실기기에서 각각 무엇을 직접 확인했는가?
- 글씨와 종이 넘김의 연속 동작에서 첫 소리 준비, 재생 시작 간격, 앞 소리의 끝을 각각 확인했는가?
- 글쓰기 리듬의 연속 입력, 짧은 쉼, 재개, 화면 이탈에서 한 재생 흐름과 음량 변화를 확인했는가?
- 도구 견본이 실제 본문과 같은 표시 함수를 쓰며, 견본만으로 사용자 기록을 만들지 않는가?
- 도구 그림과 버튼을 분리했을 때 스크린리더의 선택 상태와 실행 동작도 실제로 확인했는가?
- 1인칭 공간에서 눈 뒤의 면·근접한 가구·충돌·동작 줄이기와 화면 종료 중의
  이미지 로딩·카메라 이동·소리 해제를 함께 확인했는가?
- 공간의 자리 같은 임시 상태가 기록 저장·계정 상태와 분리되고, 공간을 오가는
  중에도 저장 완료·실패와 한글 조합 보호를 확인했는가?

**산출물**은 실제 사용 경로에 연결된 변경과 다시 확인할 수 있는 검증 기록이다.
검증 기록에는 실행 결과와 확인하지 못한 환경을 적는다.

## 요청에 적용하기

요청에 지정된 역할이 검토를 이끈다. 여러 관점이 필요한 경우에는 사용자 흐름, 화면,
구현, 사용자에게 전할 문장 중 해당 요청에 필요한 부분을 이어서 검토한다.

예를 들어 ‘iPad 가로 화면에서 원문을 보며 필사하는 흐름’을 다룰 때 기획자는 원문을 열고
쓰던 줄로 돌아오는 동작을 정한다. 디자이너는 두 면으로 펼친 시안에서 원문과 본문의 폭을
확인한다. 개발자는 회전과 키보드 전환에 본문과 입력 위치가 유지되는지 확인한다. 마케터는
그중 구현하고 확인한 경험을 iPad 소개 문구로 옮긴다.

## 작업마다 페르소나 다듬기

앱 화면, 브랜드 소개, 실물 책 시안에 같은 방식으로 적용한다. 작업을 시작할 때는 관련
역할의 기준을 읽고, 마칠 때는 사용자 피드백·시안 검토·테스트에서 배운 점을 네 역할별로 살핀다.

| 역할 | 작업을 마칠 때 살필 점 |
| --- | --- |
| 디자이너 | 글과 여백, 재질이나 조작부에서 다음 시안에도 적용할 배치·표현을 확인했는가? |
| 기획자 | 사용자가 시작하는 곳, 막히는 지점이나 이어서 쓰는 흐름에서 새로 확인한 것이 있는가? |
| 마케터 | 독자가 쓰는 말이나 실제 화면에서 다음 소개에도 근거로 삼을 표현을 찾았는가? |
| 개발자 | 입력·저장·복원이나 기기 차이를 확인하는 과정에서 다음 구현에 적용할 기준이 생겼는가? |

다음 작업에도 쓸 수 있는 판단이 생기면 해당 역할의 질문이나 설명을 바로 고친다.
맥락이 필요하면 어떤 상황에서 무엇을 확인했고 어떤 결정을 내렸는지 한두 문장으로 덧붙인다.
관련 화면·시안·검증 기록이 있으면 함께 연결한다. 확인 중인 내용은 그 상태를 밝혀 두고,
새로 반영할 판단이 없는 역할은 그대로 둔다. 공통 브랜드 원칙이 바뀌는 결정은 제품 문서에도 반영한다.

예를 들어 사용자가 필사 중 잉크 표식이 글씨를 가린다고 알려 주면, 디자이너 기준에
‘필사면의 장식은 본문과 입력 위치가 온전히 드러나는 여백에 둔다’를 반영할 수 있다.
같은 기준은 실물 책 시안에서 장식과 본문이 겹치는지 확인할 때도 쓸 수 있다.


### 아이보리 석재 적용에서 남긴 판단 · 2026-11-22

- 디자이너: 비슷한 목재를 모든 면에 반복하기보다 석재 바닥·오크 상판·월넛 프레임을
  나누고 부재의 결 방향, 둥근 모서리와 곡면을 앉은 시점에서도 확인한다. 입구 한 장의
  인상만으로 세부 품질을 승인하지 않는다.
- 기획자: 이번에는 중앙 테이블·보행·책 고르기·기존 쓰기 동선에 새 규칙을 추가하지 않았다.
  기존 직접 클릭과 입력·저장 보존 기준을 유지한다.
- 마케터: 생성 시안과 실제 Flutter 렌더를 함께 구분해 소개한다. 재질을 추가한 사실을
  사진 같은 공간 완성이나 실기기 체험 검증으로 설명하지 않는다.
- 개발자: 면 수를 늘릴 때 평균 깊이 정렬로 작은 노트·펜을 덮는 회귀도 검사한다.
  여러 이미지 재질이 모두 반복 재그리기 뒤 살아 있는지 실제 CanvasKit 엔진으로 확인한다.


## 고요한 뜰 적용에서 남긴 판단 · 2026-11-22

디자이너는 쉬는 자리에서 물체 이름표를 숨기고 나무와 연못을 바라보는 여백을 남긴다.
기획자는 벤치에 앉기와 노트를 눌러 쓰기를 별개로 두고, 기록·시간·완료를 요구하지 않는
방문을 유지한다. 마케터는 생성 시안·실제 Flutter 렌더·실기기 체험과 휴식 효과를 각각
구분한다. 개발자는 움직임뿐 아니라 방 전환·음향의 취소를 함께 검사하고, 앱을 떠나거나
동작 줄이기를 켰을 때 정지하며 복귀 때 소리가 자동으로 다시 켜지지 않는지 확인한다.


## 걷기 적용에서 남긴 판단 · 2026-11-22

디자이너는 3인칭의 캐릭터 크기를 휴대폰과 넓은 화면에서 따로 보고, 가까운 카메라와
옷/신발의 겹침·발의 접촉을 실제 렌더에서 확인한다. 기획자는 이동 중 목적지를 바꿔도
현재 위치에서 이어지고 시선 회전·앱 이탈에서 예약된 동작까지 취소되는지 검토한다.
마케터는 단순한 관절 임시 인물과 생성 이미지의 사실적인 인물을 구분한다.
개발자는 인물의 눈높이와 표시 카메라를 분리하고, 표시 카메라로 렌더·픽킹·이름표를
같이 계산한다. 벽 충돌은 시점 보간 중에도 검사하며 발 디딤은 이동 거리로 검증한다.


### 검증 빌드의 소스 고정 · 2026-11-22

개발자는 빌드 도중 자세 값을 보완한 뒤 증분 출력에 이전 값이 남는 경우를 확인했다.
검증 빌드를 시작한 뒤에는 소스를 고정하고, 추가 수정이 있었다면 캐시를 비운 새 빌드로
공개 파일과 해시를 다시 비교한다. 공개 CI의 통과와 로컬 증분 출력의 일치를 구분한다.


## 아바타 철회와 낮은 명도 바닥 시안 · 2026-11-22

사용자가 아바타는 시기상조라고 판단해 3인칭 제거를 명시했다. 기획자는 1인칭 공간과
기존 걷기를 유지하고 철회한 기능을 남겨 선택을 요구하지 않는다. 디자이너는 조도를
낮추는 대신 바닥 재질만 웜 토프/모카로 낮춰 원목·종이·빛의 대비를 같은 구도에서
비교한다. 마케터는 바닥 시안과 실제 적용을 구분한다. 개발자는 버튼만 숨기지 않고
인물/추종 카메라/보행 관절 코드를 제거하며 픽킹·경로·IME/저장 회귀 검사를 유지한다.


## 모카 바닥과 실내 마감에서 남긴 판단 · 2026-11-22

- 디자이너: 낮은 명도의 바닥을 선택해도 벽·종이와 통로의 밝기는 유지한다. 벽의
  질감·걸레받이·프레임의 두께와 실제 창 손잡이처럼 가까운 거리에서 읽히는 디테일을
  입구/앉은 자리/벽 가까이의 같은 실행 렌더에서 함께 살핀다.

  벽 마감을 사진 같은 체험이나 iPhone 실기기 검증 완료로 소개하지 않는다.
- 개발자: 가까운 종이/그림을 바꿀 때 뒷면과 표지의 넓은 불투명 면도 같이 살핀다.
  작은 면으로 분할해도 그 뒤의 큰 면이 덮을 수 있어, 보이지 않는 뒷면은 없애고
  실제 테두리만 만든다. 국소 재질 추가 후 이미지 원본/clone 수명과 반복 회전도 확인한다.


## 창가 정원 적용에서 남긴 판단 · 2026-11-22

  않는다. 정원만 분리하고 실제 창가 세 자리에서 연못 크기·경계·하늘과 여백을 본다.
